Connect your agent

The agent you already run, behind your keyboard.

If you already run an agent — on your Mac, on a VPS, or hosted somewhere — the Caret Agent Bridge puts a caret/v1 front door on it. One small server, one config switch, no third party in the middle of your typing.

To be precise about what this is: Caret does not integrate with any agent directly. Caret talks to one HTTP contract (caret/v1), and the bridge is a reference implementation of that contract's two required surfaces — health and Ask — that forwards each draft to the agent runtime you select. The table below says honestly, per runtime, how far that support has been verified.

The bridge in one minutestdlib python

A single Python file, standard library only, about seven hundred lines you can read end to end. Download it, pick a backend, generate a key: 

curl -fsSLO https://docs.typewithcaret.com/agent-bridge/caret_agent_bridge.py

export CARET_BRIDGE_BACKEND=claude-code     # hermes | codex | openclaw | custom-http
export CARET_BRIDGE_API_KEYS="$(python3 -c 'import secrets;print(secrets.token_urlsafe(32))')"
echo "$CARET_BRIDGE_API_KEYS"               # this goes into the Caret app

python3 caret_agent_bridge.py --check       # validate configuration
python3 caret_agent_bridge.py --port 8790   # run

Then put TLS in front (below) and paste the URL and key into Caret's settings.

Compatibility matrix

Three labels, used strictly:

  • Tested — the preset was run end to end against a real install of the runtime: a live draft came back through the bridge.
  • Bridge-supported — the bridge's side of the boundary is fully covered by the hermetic test suite, and the preset uses only the runtime's stock documented syntax — but the suite does not execute the real runtime.
  • Not yet verified — no stable interface could be checked, so the bridge ships no default and refuses the backend until you configure it explicitly. Not a support claim.

Where the bridge runs, and how Caret reaches it

The bridge binds loopback and speaks plain HTTP; the keyboard requires https://. So every deployment is the same shape — bridge on the machine where your agent lives, TLS in front — and the choice is only what provides the TLS.

ModeHowTrade-off
Local Mac, tailnet tailscale serve --bg 8790 gives the bridge a private https://your-mac.your-tailnet.ts.net URL. Your iPhone joins the same tailnet. Recommended default. Nothing is exposed to the public internet; TLS certificates are handled for you; works away from home. Requires Tailscale on phone and Mac.
Private VPS / hosted box, tailnet Same as above, on the box where your agent runs. Same properties; the box needs no open ports at all.
VPS, public HTTPS A reverse proxy (Caddy shown in the runbooks) terminates TLS with an automatic Let's Encrypt certificate and forwards to 127.0.0.1:8790. Works from any network with no client software — but the endpoint is publicly reachable, so the bearer key and the proxy are your entire perimeter. Use a dedicated subdomain and keep the bridge itself on loopback.
Not recommended

Port-forwarding your home router at the bridge, or binding the bridge to 0.0.0.0 without a proxy. The bridge fronts an agent with an API key as the only lock; keep it off the open internet unless a proxy and a dedicated host are in front of it.

Pairing and the key model

Pairing is deliberately boring: a base URL and a bearer key, both entered once in Caret's settings.

  1. Generate a key on the machine that runs the bridge — python3 -c 'import secrets;print(secrets.token_urlsafe(32))'. Put it in CARET_BRIDGE_API_KEYS. One key per device makes revocation a matter of deleting one string and restarting.
  2. Enter URL and key in Caret. The app calls GET /v1/health — the only anonymous endpoint — and shows you what it found: auth.valid tells "wrong key" apart from "wrong URL", and capabilities tells the keyboard the bridge is text-only, so it never offers a microphone the bridge cannot serve.
  3. Every draft is authenticated with Authorization: Bearer, compared in constant time. No keys configured means the bridge fails closed: every draft is 401 and health reports degraded.

Security model

What the bridge promises, and what stays your responsibility:

  • Text-only, two endpoints. The bridge implements health and Ask, declines audio with a contract error, and reports {"dictation": false, "imagine": false}. There is no surface it half-supports.
  • It never widens your agent's permissions. The CLI presets use each runtime's documented non-interactive, most-restricted mode — Claude Code in read-only plan mode, Codex in a read-only sandbox. The bridge refuses to start if a configured command contains a known permission-bypass flag (--dangerously-skip-permissions, danger-full-access, …). It never enables tool actions, arbitrary shell execution, or background work on the agent's side.
  • A prompt is not a sandbox. The drafting prompt tells the agent it is writing a draft, not acting — but for runtimes whose restriction flags are advisory (Hermes toolsets follow your profile), the runbook shows the documented way to narrow them, and recommends running the bridge as a dedicated low-privilege user with its own agent profile. That recommendation is the default posture, not an extra.
  • No secret or content logging. Access logs carry method, path, status, latency and request_id — never instructions, drafts, near-cursor text, or keys. This is asserted by the test suite, not just promised.
  • What your agent sees per draft: the instruction you typed, up to 4000 characters of text near the cursor (visible_text, often empty), and the host app's bundle id as a register hint. Near-cursor text is someone else's words — the framing treats it as untrusted context, never as a command.
  • Timeouts, not hangs. Every draft has a wall-clock budget (90 s default); overrun is a clean 504 draft_timeout, and a failed draft is never cached — retries can succeed.

Troubleshooting, from the outside in

SymptomMeaning
Bridge exits immediately with configuration error: … The message says exactly which variable to fix. --check reproduces it without serving.
Caret says it cannot reach the URL TLS layer. curl https://…/v1/health from the phone's network; if that fails, fix the proxy/tailnet before touching the bridge.
Health shows "valid": false Key mismatch between the app and CARET_BRIDGE_API_KEYS.
Health shows "status": "degraded" No keys configured; the bridge is failing closed as designed.
503 internal_error: … exited N The agent CLI failed; the stderr tail is in the message. Run the runbook's smoke command by hand as the bridge's user.
504 draft_timeout The agent is slower than CARET_BRIDGE_TIMEOUT_S. Pin a faster model in the command, or raise the budget.

Every response carries a request_id; the bridge logs one line per request with the same id, so a report from the keyboard gives you a grep target.
