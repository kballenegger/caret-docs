caret/v3 · optional · live dictation

Live dictation over one WebSocket.

A backend that runs a streaming speech recognizer can show the user their words while they speak: the keyboard holds one authenticated WebSocket open for the whole dictation, streams raw audio frames up, and receives partial transcripts the moment speech is recognized — then exactly one terminal result. This surface is optional and additive: a backend without it is still fully conforming, and a backend with it must still serve the V2 REST session endpoints, which remain the recovery path for backgrounding, offline, and retries.

V2 is the contract; V3 is the fast path.

The live socket exists for latency, not durability. It keeps no state beyond the connection: no session directory, no cached result, no ACK step. If anything interrupts the socket, the client re-submits the same audio through POST /v2/sessions + chunk uploads and loses nothing. Never implement V3 instead of V2.

Endpoint, auth, discovery

WhatDetail
Endpoint wss://<base-url>/v3/dictate — same base URL the user configured, TLS required, WebSocket upgrade.
Auth Authorization: Bearer <key> on the upgrade request — the same key and comparison rules as every V2 endpoint. An invalid key gets an error event (unauthorized) and close code 4401.
Discovery Advertise "live_dictate": true inside capabilities on GET /v2/health. Absent means false; the keyboard then uses V2 sessions only.
Audio pcm16 little-endian, 16 kHz, mono — identical to V2 chunks.

Client → server frames

FrameContent
text start {"type": "start", "protocol": 1, "codec": "pcm16", "sample_rate_hz": 16000, "channels": 1, "polish": true, "client_request_id": "…"} — must be the first frame, within 10 s of connecting. polish (default true) runs transcript cleanup on the final; client_request_id, app_hint, and language_hint are optional strings with the V2 length caps.
binary Raw audio, in capture order — WebSocket message order is the audio order. At most 512 KiB per frame; empty frames are ignored. Frame boundaries carry no meaning; send whatever cadence the recorder produces (~100–500 ms works well).
text finish {"type": "finish"} — no more audio. The server flushes the recognizer and answers with the terminal event.
text cancel {"type": "cancel"} — abandon. The server discards everything and closes 1000 with no terminal event.

Server → client events

All events are text JSON and carry the session_id the server assigned for this connection.

EventContent
opened {"event": "opened", "protocol": 1, "session_id": "live_…", "request_id": "req_…", "stt": "streaming" | "buffered"} — answers a valid start. "buffered" means the streaming recognizer is unavailable right now: no partials will come, audio is still accepted, and the final is produced by the fallback at finish. The client needs no special handling beyond not waiting for partials.
partial {"event": "partial", "session_id", "seq", "frames", "text", "segment", "segments"} — pushed immediately, one per recognizer update. text is the cumulative transcript of the whole dictation, not a delta: render it as-is, replacing the previous partial. seq is a monotonic counter (drop anything out of order after a client-side race), frames counts audio frames consumed so far, and segment/segments expose the recognizer's endpoint detection — the engine may reset its own text at a segment boundary, but the server re-accumulates, so text never goes backwards across segments.
final {"event": "final", "session_id", "request_id", "text", "route": "stream" | "fallback", "duration_ms", "frames"} — exactly one, after finish. text has cleanup applied (unless polish: false) and supersedes every partial. The server then closes 1000.
error {"event": "error", "session_id", "request_id", "code", "message", "retryable"} — terminal; the server closes with the mapped code below. Codes are stable and append-only, like V2's.

final and error are mutually exclusive and always sent after any queued partials, so the last text the client holds is the authoritative one.

Reconnect: the connection is the session

Server-side state is one bounded in-memory audio buffer plus the live recognizer connection, and both are destroyed when the socket closes — whoever closes it. There is no resume token and no persisted result. That is deliberate: it keeps retention at zero and it never competes with V2's durability story.

  • Socket drops before final: the server-side transcript of that connection is gone. The client keeps its own audio (it already buffers chunks for V2) and re-submits through V2 REST sessions. Reconnecting to V3 always starts a fresh session with a fresh session_id.
  • App backgrounded / network changed mid-dictation: same answer — V2 is the recovery path, and it produces the same transcript from the same audio.
  • Terminal error received: nothing to clean up; a retryable: true code may be retried on a fresh connection, otherwise submit via V2.

Fallback: streaming first, merged audio second

A streaming failure must never kill the dictation. The server buffers every audio frame it accepts, independent of the recognizer, and uses the buffer when streaming lets it down:

  • Recognizer unreachable at start → opened says "stt": "buffered"; no partials, everything else proceeds.
  • Recognizer fails mid-stream → partials stop; the session lives on.
  • Recognizer fails at flush → same.

In every case finish transcribes the merged buffered audio through the backend's batch STT (and whatever fallback chain V2 dictation already has), then applies the same cleanup, and the final reports "route": "fallback". One rule matters for correctness: an empty transcript from a healthy stream is no_speech_detected, never a fallback trigger — silence is an answer, not an error.

Retention and privacy

Audio is retained in memory only, bounded (600 s of pcm16 ≈ 19 MB), and dies with the connection. If the fallback needs a file for batch STT, it must be temporary and deleted the moment transcription returns. Partial transcripts exist only in the recognizer connection and the socket frames. Do not log transcript, partial, or audio content; log ids, counts, and timings. V3 writes no session directory, caches no result, and therefore has no ACK/purge step — V2's retention semantics are untouched.

Implementer checklist

  • Advertise capabilities.live_dictate: true only when the socket is actually served.
  • Bearer auth on the upgrade request; same keys, same constant-time comparison as V2.
  • Enforce the caps: start within 10 s, 512 KiB per frame, bounded total audio, an idle timeout between frames.
  • Accumulate recognizer output by segment id so text is cumulative across endpoint resets.
  • Exactly one terminal event, after all queued partials; close 1000 on final/cancel, the mapped 4xxx code on error.
  • Buffer audio independently of the recognizer; fall back to merged audio only on streaming failure, never on empty text.
  • Keep V2 sessions fully working — the keyboard depends on them the moment anything goes wrong live.

The V2 wire contract stays authoritative in openapi.yaml (which also documents the related V2 additions: stt_streaming on session open and the per-chunk stt partial object). Where this page and the OpenAPI document overlap, the OpenAPI document wins.
