caret/v4 · reference implementation · design

The public reference backend, by design.

This page specifies the public caret/v4 reference implementation: what it will be, what it will refuse to be, and how its pieces fit. It exists so that the code, when it lands in this repository, has a contract of its own to be judged against.

Status: design. There is no code to download yet.

Nothing on this page is shipped, and nothing on it has been tested, because it does not exist yet. The caret/v4 protocol itself is not hypothetical — Caret's own production backend implements it end to end — but that implementation is private and is not this design. Until the public reference lands, implement V4 directly from the protocol page; it is written to be sufficient on its own. The archived V2 reference backend remains available but speaks a retired contract.

Goals, in order

  1. Readable before runnable. Like the archived V2 backend, it is meant to be read: every rule on the protocol page implemented once, in an obvious place, in a codebase small enough to hold in your head.
  2. Dependency-light. Standard library plus, at most, one WebSocket library where the standard library has none. No framework, no build pipeline, no container required.
  3. Pluggable lanes, honest capabilities. Speech, agent, and image providers plug in behind narrow interfaces; whatever fails to resolve is reported off in /health rather than papered over — the same capability-routing discipline the V2 backend proved out.
  4. A conformance checker, not just a server. The deliverable is as much the harness that can interrogate any V4 backend as it is the backend itself.

Shape

  conformance   the checker: drives a live backend through the
                lifecycle, the reliability rules, and the error table
  tests         hermetic; loopback only, no model calls

Design decisions already fixed

DecisionRationale
One lifecycle state machine shared by all three routes The protocol says the routes differ only in finalizer and result type; the code should prove that by construction.
Audio buffer independent of the recognizer §8 of the protocol makes fallback mandatory; the buffer is the server's half of the reliability contract.
Dictate-only is the default build A conforming backend needs speech and nothing else. Agent and image lanes activate only when configured, and /health says so.
Vocabulary reaches both the recognizer and cleanup Advertising "vocabulary": true while dropping the list is forbidden by the protocol; the lane interfaces carry it explicitly so no provider can lose it silently.
Zero retention by default In-memory audio, bounded; cached results expire in minutes; no transcript logging. Matching §10 exactly.

The conformance checker

The checker will treat the backend under test as a black box at a base URL — any language, any host — and exercise what is easy to get subtly wrong: audio-total verification and audio_incomplete, exactly-one-terminal-event ordering after queued partials, cumulative (never regressing) partial text, replay with a repeated client_request_id, honest capabilities versus served routes, and the full error table with its close codes. Exit 0 will mean a V4 client will be happy.

What it will not be

  • Not a hosted service, not a relay — the protocol has no privileged party, and neither will the reference.
  • Not a fork target for the cleanup wording: the spec is consumed as data from spec/cleanup/v1/, digest-checked.
  • Not a V2 compatibility layer. Operators who need V2 during cutover run the archived backend beside it — see migration.

When the implementation lands, this page becomes its README's front door and gains the run instructions; until then, treat every command and path above as design, not documentation of something you can download.
