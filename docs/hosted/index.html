Caret API · hosted · dictate only

The hosted Caret API.

https://api.typewithcaret.com is the service behind the app's Caret API mode: paste an API key, dictate. It serves one operation, live dictation on wss://api.typewithcaret.com/v4/dictate, plus a small REST surface for your personal dictionary. This page is the wire contract of that service, for people writing their own client or debugging a connection. If you want to run a backend, you want the open protocol instead.

Two contracts, one name.

The hosted service and the open caret/v4 protocol both call themselves caret/v4, and they are not the same wire. The hosted service answers GET /health with "contract": "caret/v4" and dictates on /v4/dictate. An open-protocol backend answers with "protocol": "caret/v4" and serves /dictate, /ask, /imagine at the root. The keys differ on purpose so a client can never mistake one for the other. The hosted root has no /dictate; it returns 404.

1 · Setup in the app

Choose Caret API as the backend mode, create an account at typewithcaret.com/signup, and paste the key. There is no URL to enter: the base URL is fixed. The key travels as a Bearer token and is stored in the device Keychain. The app's other two modes are Offline (on-device recognition, nothing to configure) and Your Agent (a backend you run, speaking the open protocol); see the overview.

Caret API mode is dictate only. The Ask and Imagine surfaces are not offered on the hosted service; they need a Your Agent backend that advertises them.

2 · Health

GET /health · GET /v4/health · HTTPS, no auth required

The two paths return the same report. The root path is the reachability probe a client can hit before it knows which route family a host serves; the current Caret app probes /v4/health in Caret API mode. Send Authorization if you have a key and the report tells you whether it was accepted. 

{
  "status": "ok",
  "contract": "caret/v4",
  "version": "1.2.0",
  "auth": {"presented": true, "valid": true},
  "capabilities": {"dictate": true, "codecs": ["opus", "pcm16"], "resume": true},
  "cleanup": {"enabled": true, "spec": "caret-cleanup/1 20ab781577580c29"},
  "debug_capture": {"enabled": false},
  "request_id": "req_17d6cab18cf7cb59"
}
  • contract is exactly "caret/v4". There is no protocol key; that is the open protocol's discriminator and the root does not serve those routes.
  • status is ok or degraded (reachable, but the recognizer is not configured).
  • auth: with no header, {"presented": false, "valid": null}; with one, whether the key is live. A settings screen uses this to tell "wrong key" from "wrong URL".
  • capabilities.codecs lists what you may offer in start. pcm16 is always present; opus is preferred when listed. resume says a dropped session can be resumed (§5).
  • cleanup.spec names the transcript-cleanup wording by its published digest, never the prompt itself. See the cleanup spec.
  • debug_capture.enabled reports whether the deployment's diagnostic capture switch is on. It is a status flag; this page does not describe what the service stores or for how long. The service's own terms do.
  • Only GET is served; anything else is 405. Every other legacy path (/v1/, /v2/ operations, /v3/) is 404.

3 · Auth

GET /v4/dictate HTTP/1.1
Upgrade: websocket
Authorization: Bearer <API key>

One mechanism, everywhere: an Authorization: Bearer header on the WebSocket upgrade request and on every dictionary request. No query parameter, no WebSocket subprotocol, no signed proof, no nonce. The client-proof scheme an earlier hosted API required is gone with the server that spoke it; the current service neither accepts nor expects it.

On the WebSocket the upgrade succeeds first (HTTP 101) and the key is checked after. A missing or invalid key gets an error event with "code": "unauthorized" and close code 4401, so check the first frame and the close code, not the upgrade status. If the service cannot reach its account store the answer is internal_error (4500, retryable), never a false "wrong key".

start

The first text frame, within 10 seconds of the upgrade:

{
  "type": "start",
  "protocol": 2,
  "codecs": ["opus", "pcm16"],
  "sample_rate_hz": 16000,
  "channels": 1,
  "client_request_id": "A17C…",    // optional
  "app_hint": "com.apple.MobileSMS", // optional
  "language_hint": "en-US",          // optional
  "polish": true                     // optional, default true
}
  • protocol is the integer 2. This is the hosted wire's own version number and has nothing to do with the open protocol's "protocol": 4. Any other value is a protocol_error.
  • codecs is required and non-empty. The server picks opus if both sides offer it, else pcm16; no common codec is unsupported_codec.
  • sample_rate_hz, if sent, must be 16000; channels, if sent, must be 1.
  • polish: false skips the cleanup pass and returns the recognizer's raw text with "cleaned": false.
  • Vocabulary is not sent on this wire. Hosted accounts keep a dictionary on the server (§7) and it is applied automatically.

opened

{"event": "opened", "protocol": 2, "session_id": "live_…", "request_id": "req_…",
 "codec": "opus", "stt": "streaming", "resume_token": "rt_…",
 "ack_every": 8, "reorder_window": 64, "max_frame_bytes": 524288}

codec is the negotiated one. stt is "streaming" when live partials will come and "none" when they will not; the terminal transcript is produced either way. Keep resume_token until the terminal event.

Audio frames

Every binary message carries an 8-byte big-endian header, then the codec payload:

OffsetSizeMeaning
01magic 0xC4
11flags; bit 0 set means retransmit
22reserved, zero
44unsigned frame sequence number
  • Sequence starts at 0 and increases by one in capture order. pcm16 is little-endian 16 kHz mono; opus is a standard Ogg-Opus stream split across ordered payloads.
  • Empty payloads are ignored. A payload over max_frame_bytes is a terminal bad_request. A malformed header is a terminal protocol_error.
  • Replayed frames are idempotent; the recognizer is never fed out of sequence. Setting the retransmit flag on a resend is recommended and is required after finish (§5).

partial, ack, nack

{"event": "partial", "session_id": "live_…", "seq": 7, "frames": 18,
 "text": "cumulative words so far", "segment": 1, "segments": 2}
{"event": "ack",  "session_id": "live_…", "contiguous_seq": 12, "received": 12, "duplicates": 0}
{"event": "nack", "session_id": "live_…", "contiguous_seq": 12, "missing": [12, 13]}
  • partial.text is the cumulative transcript so far, never a delta; render it in place of the previous one. seq is monotonic per session. Partials are preview only and are never the terminal transcript.
  • ack arrives every 8 contiguous frames by default (the ack_every from opened) and immediately when a retransmit fills a gap. Frames below contiguous_seq are safely received and the client may drop them.
  • nack names missing sequence numbers, at most 64 per event.

finish and cancel

{"type": "finish", "frames": 42}
{"type": "cancel"}

finish.frames is the exact number of frames captured, numbered 0..frames-1. After finish the server nacks anything missing and waits 5 seconds for retransmits; in that window it accepts only retransmit-flagged frames or cancel. A new, unflagged frame after finish is a terminal protocol_error. cancel closes with 1000 and no terminal event.

final and error

{"event": "final", "session_id": "live_…", "request_id": "req_…",
 "text": "Cleaned transcript.", "route": "whisper", "cleaned": true,
 "codec": "opus", "duration_ms": 4210, "frames": 42}

{"event": "error", "session_id": "live_…", "request_id": "req_…",
 "code": "transcription_failed", "message": "…", "retryable": true}

Exactly one of these ends the session, after any queued partials, and then the socket closes. final.text is produced from the complete recording after finish, with the account's dictionary as recognizer context. When cleanup ran, cleaned is true; when it failed, timed out, or polish was false, text is the raw recognition and cleaned is false. Cleanup never turns a good transcript into an error. route names the transcription path that produced the text.

5 · Reliability: acks, reorder, resume

The open protocol puts durability on the client and replays whole operations. The hosted wire is finer grained: per-frame sequence numbers, acknowledgements, and a resumable session.

  • Out-of-order frames wait in a bounded window, 64 frames or 4 MiB. Beyond that the session fails with reorder_overflow (retryable).
  • A disconnect before the terminal event parks the session for 45 seconds. Reconnect and send {"type": "resume", "protocol": 2, "resume_token": "rt_…"} as the first frame. The reply is opened plus contiguous_seq and a freshly rotated token; the old one is single use and bound to the same key. Resend everything above contiguous_seq; duplicates are never re-recognized.
  • An expired or reused token is resume_invalid (4410). Start over with a new session; the audio you still hold is the recovery.
  • A rate_limited resume is retryable and does not burn the token.

7 · The hosted dictionary

GET /v2/dictionary · POST /v2/dictionary · PUT /v2/dictionary/{id} · DELETE /v2/dictionary/{id} · Bearer auth

A per-account list of terms the recognizer and the cleanup pass should spell your way, up to 200 entries. Each entry is {"id": "dict_…", "term": "…", "notes": "…", "created_at": "…", "updated_at": "…"}; term is at most 64 characters and notes at most 200. GET returns {"entries": [...], "max_entries": 200}. POST takes {"term", "notes"?}. PUT takes {"term"?, "notes"?}, where an omitted notes leaves it alone and an explicit null clears it. DELETE returns {"id", "deleted"}. Terms feed only your own dictations.

Errors use one envelope on every REST route:

{"error": {"code": "dictionary_full", "message": "…", "retryable": false},
