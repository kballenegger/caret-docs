compatibility · cutover

Moving to caret/v4.

caret/v4 replaces both caret/v2 (REST, chunked sessions) and caret/v3 (the optional live-dictation WebSocket). If you are building something new, ignore this page and implement V4. If you operate a pre-V4 backend or maintain a client that speaks V2, this is the cutover plan.

What actually changed

caret/v2 + v3caret/v4
REST operations (POST /v2/dictate …) over chunked audio sessions, with V3 live dictation as an optional fast path The live socket is the protocol: three WebSocket routes sharing one lifecycle, live partials for everyone, no REST session machinery at all.
Durability on the server: session directories, cached results, ACK/purge, missing-chunk repair Durability on the client: it keeps the audio and replays the operation on a fresh connection; finalize audio totals prove completeness; client_request_id keeps replays from double-billing.
Two-step spoken input (upload session, then call the operation) One step: connect to the route, stream, finalize.
Untyped result objects, per-endpoint shapes Typed terminal results: "dictation", "message", "image" — one per route.
GET /v2/health, "contract": "caret/v2" GET /health, "protocol": "caret/v4", with per-route partials/text_input capabilities and advertised limits.
Vocabulary: none (glossary fixed in the cleanup spec) Per-operation vocabulary injection into STT biasing and the cleanup glossary.

What did not change: TLS-only, bearer presentation with the backend owning the credential scheme, PCM16/16 kHz/mono audio, dictate mandatory with capabilities honest, append-only error codes with a truthful retryable, unknown JSON fields ignored, and caret-cleanup/1 as the cleanup wording — that spec is versioned independently and is untouched by V4.

Side-by-side serving

V4 routes are unversioned (/health, /dictate, /ask, /imagine); every pre-V4 path carried a /v2/ or /v3/ prefix. They cannot collide, so one base URL can serve both contracts during a cutover — a reverse proxy that routes by path prefix is enough: 

/health, /dictate, /ask, /imagine   →  V4 backend
/v2/*, /v3/*                        →  legacy backend (archived)

Clients decide by discovery, not guessing: a V4 client calls GET /health and proceeds only on "protocol": "caret/v4"; a V2 client calls GET /v2/health and never sees the V4 surface.

Cutover: backend operators

  1. Stand up V4 against the protocol page. If you would rather start from working code than from the spec, the public reference backends in Go and Python run in one command and take real recognizers and agents through a lane flag.
  2. Run the conformance checker against your base URL (go run ./cmd/caret-v4-conform -url … -key … from reference/go, or python3 -m caret_v4 conform). It is the runnable form of the §11 checklist. Then verify with a current Caret release in Your Agent mode.
  3. Keep /v2/ alive only while a pre-V4 client still uses it. If your only client is a current Caret build, skip straight to V4-only.
  4. Retire the legacy surface: stop routing /v2/*, decommission the old backend, and rotate any credentials that were shared between the two.

Cutover: client developers

  1. Implement V4 only — do not add V2 support to a new client. The client-side conformance list is §11 of the protocol.
  2. Treat /health without "protocol": "caret/v4" as "not a V4 backend" and say so to the user; do not silently probe /v2/health.
  3. Own durability: buffer captured audio until a terminal result is held, replay on transport failure, honor cached replays.

Where the old material lives

The pre-V4 documentation is no longer published on this site; its old URLs land on a short retirement notice. The material itself, the V2 implementation guide, the V3 live-dictation spec, the connect runbooks, the archived openapi.yaml, the V2 reference backend and its packaged integrations, stays in the repository under legacy/ for operators who still run a pre-V4 backend. None of it applies to V4 except as history.
