The advanced path

Most people do not need this page: to put the agent you already run behind your keyboard, deploy the reference backend instead. This page is for implementing caret/v2 from scratch — point your coding agent at the implementation prompt if you want it built for you.

caret/v2 · contract 2.0 · advanced

Implement the Caret API.

Everything the keyboard sends and everything it expects back, in the order you would build it. Three product operations over one mode-neutral audio transport. Health, the session endpoints, and Dictate are required; Ask and Imagine are optional. The machine-readable version of this page is openapi.yaml — where the two disagree, the OpenAPI document wins.

caret/v1 is deprecated and no longer documented; V2 is the only supported contract.

Dictate is mandatory. Ask and Imagine are not.

A caret/v2 backend takes speech. It must advertise "dictate": true and serve the session endpoints plus POST /v2/dictate; anything that cannot is not a Caret backend and must report "status": "not_ready" rather than dress itself up as one. Ask (/v2/ask) and Imagine (/v2/imagine) are each optional: report false and answer 404 not_found if you do not serve them.

So the shortest valid backend is GET /v2/health, the session endpoints, and POST /v2/dictate, declaring {"dictate": true, "ask": false, "imagine": false}. The shape this contract does not accept is the mirror image of that — Ask on with Dictate off.

Ground rules

RuleDetail
Base URL Whatever the user enters in Caret. Paths are appended verbatim, so https://host/caret means https://host/caret/v2/health.
Transport https:// is required. Terminate TLS wherever you like — a reverse proxy or a private tunnel is fine.
Versioning The path carries the version. Additive changes stay in /v2; anything breaking becomes /v3. Ignore JSON fields you do not recognise — the keyboard does.
Auth Authorization: Bearer <key> on every endpoint except health. Compare in constant time.
Content type application/json, except chunk upload, which is application/octet-stream.
Correlation Every response — success or failure — carries a server-generated request_id.
Client header Caret sends X-Caret-Client: caret-keyboard/<version> …. Log it; do not branch on it.

1 · Health and capabilities

GET /v2/health — no auth

Called on every settings save and periodically while the keyboard is in use. It is the only anonymous endpoint: a user pasting a URL needs to find out whether it is a Caret backend before they have a key. 

{
  "status": "ok",
  "service": "my-backend",
  "contract": "caret/v2",
  "version": "2.0.0",
  "time": "2026-08-06T11:40:20Z",
  "auth": {"presented": true, "valid": true},
  "capabilities": {
    "dictate": true,
    "ask": true,
    "imagine": false,
    "input_modes": {
      "dictate": ["text", "session"],
      "ask": ["text", "session"],
      "imagine": []
    }
  },
  "readiness": {"ready": true, "blockers": []}
}
  • status is ok, degraded or not_ready. degraded means reachable but impaired — the keyboard shows a warning, not a failure. not_ready means this is not a usable Caret backend: report it whenever capabilities.dictate is false, because Dictate is mandatory.
  • readiness says why, in codes rather than prose, so a setup tool can act on it: {"ready": false, "blockers": [{"code": "no_stt_adapter", "message": "…"}]}. Defined codes are no_stt_adapter and no_api_keys; clients ignore ones they do not know.
  • auth.presented / auth.valid let the settings screen tell "wrong key" apart from "wrong URL". With no Authorization header, report {"presented": false, "valid": null}.
  • capabilities drives the UI. Report what you can actually do right now — an operation you advertise and cannot serve fails in the user's hands.
  • capabilities.input_modes is per operation and names the accepted input.type values, "text" and "session". List only ["text"] for an operation, or an empty array, and the keyboard will not offer its microphone there.
  • routes is optional and free-form: a place to describe how you serve each operation, for operators rather than for the keyboard. The reference backend uses it to name the cleanup wording it runs, by digest — "routes": {"dictate": {"cleanup": {"spec": "caret-cleanup/1 20ab781577580c29", "glossary_terms": 12}}}. Publish the digest, never the prompt, and never anything secret: health is anonymous. See the cleanup spec.

2 · One input model

Every operation — Dictate, Ask, Imagine — accepts the same discriminated input object. There are no per-operation audio routes and no top-level aliases: anything but the two shapes below is 422 input_invalid. 

{"input": {"type": "text",    "text": "tell Sam I'm running ten minutes late"}}

{"input": {"type": "session", "session_id": "sess_9f2c4d",
           "client_chunk_count": 4, "client_total_duration_ms": 11200,
           "polish": true}}
FieldTypeNotes
type"text" | "session"Discriminator. Required.
textstringText input only. 1–4000 characters.
session_idstringSession only. An audio session you have already accepted chunks for.
client_chunk_countinteger ≥ 1Session only, required. How many chunks the client uploaded — the completeness check.
client_total_duration_msinteger ≥ 1Session only, required. The client's own measure, advisory.
polishbooleanSession only, default true. Run transcript cleanup after STT; false keeps the raw transcript.

3 · Dictate — required

POST /v2/dictate

The mandatory operation, in both its shapes. With input.type: "session" it seals, transcribes, and consumes the audio session and returns the cleaned transcript. With input.type: "text" it runs the same transcript-cleanup pass over raw text the client already has — idempotent by client_request_id. A deployment that cannot transcribe answers 404 not_found, reports "dictate": false, and is not_ready.

Cleanup itself is specified separately, as data: caret-cleanup/1. The short version is that the transcript is handed to the model as inert data inside a <transcript> envelope, meaning is preserved completely, only formatting changes, dictated code and URLs come back as plain text with no Markdown fences added — and any cleanup failure returns the raw transcript rather than an error. If you publish which wording you run, publish the spec digest, never the prompt. 

// request
{
  "client_request_id": "A17C…",
  "input": {
    "type": "session",
    "session_id": "sess_9f2c4d",
    "client_chunk_count": 4,
    "client_total_duration_ms": 11200,
    "polish": true
  }
}

// response
{
  "status": "complete",
  "input_type": "session",
  "text": "Let's push the review to Thursday afternoon.",
  "session_id": "sess_9f2c4d",
  "missing_chunks": [],
  "duration_ms": 11200,
  "request_id": "req_5a09de"
}

client_chunk_count is how the client tells you it is done and how you detect gaps. If chunks are missing, that is not an error — answer 200 with status: "missing_chunks" so the client can upload exactly what is absent and call again: 

{"status": "missing_chunks", "input_type": "session", "text": null,
 "session_id": "sess_9f2c4d", "missing_chunks": [2], "request_id": "req_5a09de"}

A missing_chunks answer binds the session to Dictate but does not seal it — more audio is exactly what it asked for. Only a terminal result seals it (see §5).

4 · Ask

POST /v2/ask — optional

An instruction becomes one message, ready to insert. The user sees the result before it lands in the text field, so your job is to return the message itself — no preamble, no quotation marks, no markdown fence.

Request

{
  "client_request_id": "5F2A…",          // required, ≤128 chars, idempotency key
  "input": {"type": "text", "text": "tell Sam I'm running ten minutes late"},
  "visible_text": "sam: still on for 3?", // optional, ≤4000, text near the cursor
  "app_hint": "com.apple.MobileSMS"       // optional, ≤200, soft register hint
}

visible_text is what the keyboard can see near the cursor — often nothing, and never the whole conversation. Treat it as a register hint, not as context you can rely on. app_hint is a bundle identifier; use it to pick a tone, never to gate behaviour.

Response

{
  "status": "complete",
  "input_type": "text",
  "text": "Hey Sam, I'm running about ten minutes late.",
  "request_id": "req_414d33"
}

The typed path is synchronous and idempotent by client_request_id. text is only ever null on a session-input missing_chunks answer.

The same operation, spoken

POST /v2/ask
{
  "client_request_id": "B92E…",
  "input": {
    "type": "session",
    "session_id": "sess_9f2c4d",
    "client_chunk_count": 4,
    "client_total_duration_ms": 11200,
    "polish": true
  }
}

→ 200
{
  "status": "complete",
  "input_type": "session",
  "text": "Thursday afternoon works — shall we say 2pm?",
  "session_id": "sess_9f2c4d",
  "transcript": "let's push the review to thursday afternoon",
  "missing_chunks": [],
  "duration_ms": 11200,
  "request_id": "req_c31f07"
}

Return transcript alongside text. The keyboard shows the user what it heard, which is how they tell a mis-hearing apart from a bad answer.

5 · The audio transport — required

This is the part no backend may skip. Sessions are mode-neutral: a session does not know which operation will consume it. The client records into a session, uploads chunks, and then hands the session id to whichever operation the user asked for. There is no finalize or transcript endpoint — the operation itself consumes the session.

Optional fast path: V3 live dictation.

A backend with a streaming recognizer can additionally serve the caret/v3 live-dictation WebSocket — partial transcripts while the user speaks, one terminal result. It is additive: advertise it with capabilities.live_dictate, and keep these V2 session endpoints working — they remain the recovery path for backgrounding, offline, and retries. 

POST /v2/sessions                      → session_id
PUT  /v2/sessions/{id}/chunks/0, /1, … → as the user speaks
  ├── POST /v2/dictate {input:{type:"session", …}}  → transcript
  ├── POST /v2/ask     {input:{type:"session", …}}  → answer + transcript
  └── POST /v2/imagine {input:{type:"session", …}}  → image + transcript
        (the operation seals + transcribes + consumes the session —
         one terminal result; afterwards everything else is 409)
POST /v2/sessions/{id}/ack             → optional: purge server-side data

Open a session

POST /v2/sessions

// request
{
  "client_request_id": "A17C…",
  "codec": "pcm16",          // pcm16 only
  "sample_rate_hz": 16000,   // fixed
  "channels": 1,             // fixed
  "intent": "ask",           // advisory: dictate | ask | imagine
  "app_hint": "com.apple.MobileSMS",
  "language_hint": "en-US"   // optional, ≤16 chars
}

// response
{
  "session_id": "sess_9f2c4d",
  "chunk_max_bytes": 524288,
  "chunk_target_duration_ms": 3000,
  "expires_at": "2026-08-06T12:40:20Z",
  "request_id": "req_31c0aa"
}

intent tells you which operation expects to consume the session, which is useful for warming a model — but it is advisory and never enforced: the session may still be consumed by any single operation. Sessions live one hour; the client opens a new one after that. Replaying a client_request_id must return the same session rather than stranding audio in an orphan.

Upload chunks

PUT /v2/sessions/{session_id}/chunks/{seq}

Content-Type: application/octet-stream
X-Caret-Chunk-SHA256: 3f786850e387550fdab836ed7e6dc881de23001b
X-Caret-Chunk-Duration-Ms: 3000

<raw PCM16, little-endian, 16 kHz, mono>

Chunks are uploaded while the user is still speaking, roughly one every three seconds, numbered from 0. The X-Caret-Chunk-SHA256 header is mandatory and verified. Each upload is idempotent per (session_id, seq), because a phone on a flaky network retries. Two rules make that safe, and they are worth keeping distinct:

  • The body does not match its own X-Caret-Chunk-SHA256: 409 chunk_checksum_mismatch, retryable: true. The transport corrupted it; sending it again may work.
  • The digest is valid but differs from a chunk you already stored at that seq: 409 chunk_seq_conflict, retryable: false. The client has a bug; retrying cannot fix it.

An identical re-upload is a 200 with "duplicate": true. Over chunk_max_bytes is 413 chunk_too_large. A chunk sent to a session that has already been consumed is 409 session_conflict. 

{"session_id": "sess_9f2c4d", "seq": 0, "accepted": true,
 "duplicate": false, "request_id": "req_88b1c2"}

Atomic consumption

Calling Dictate, Ask, or Imagine with a session id atomically seals the session (further chunk uploads are rejected), transcribes it, consumes it, and applies the operation. A session carries exactly one terminal result:

  • A second operation on the same session — even the same one under a different job — gets 409 session_conflict.
  • A chunk upload after consumption gets 409 session_conflict.
  • Terminal results — success and failure — are cached on the session, so re-POSTing the identical body replays the same response and never re-runs work. To retry after a terminal failure, open a new session.

Acknowledge (optional)

POST /v2/sessions/{session_id}/ack

Deletes all server-side session data — audio and the cached terminal result. Idempotent: replays answer "already_acknowledged": true. ACKing a session that was never consumed is allowed and acts as abandon+purge. Plain BYOB deployments may rely on the TTL instead; zero-retention deployments treat ACK as the sole deletion trigger for a completed result.

6 · Async work

Anything that may take a while — transcription, generation — uses one convention across every endpoint. Answer 202 while the work is running: 

HTTP/1.1 202 Accepted
Retry-After: 3

{"status": "in_progress", "session_id": "sess_9f2c4d",
 "started_at": "2026-08-06T11:40:20Z", "elapsed_seconds": 3.2,
 "retry_after_seconds": 3, "request_id": "req_c31f07"}

The client polls by re-POSTing the identical body. There is no job id and no second endpoint: the request is the handle. That puts three requirements on you.

  • request_id is stable from the first 202 through the terminal response. It identifies the work, not the HTTP round trip.
  • Re-posting never starts a second job. Register the job and check for an existing one under one lock, or a client that polls twice pays twice.
  • Terminal results are cached — successes and failures both. A failed generation that silently re-runs on the next poll is a surprising bill.

Doing the work synchronously is fine if you can finish inside the client's timeout; 202 is a tool, not an obligation.

7 · Imagine

POST /v2/imagine — optional

Same input model as everything else: {"type": "text"} or {"type": "session"}, the latter consuming an audio session exactly as above. Always asynchronous: expect 202 + Retry-After and poll by re-POSTing the identical body. If you do not implement it, report "imagine": false in capabilities and answer 404 not_found — that is a conformant backend. 

// request
{
  "client_request_id": "C40D…",
  "input": {"type": "text", "text": "a lighthouse at dusk, watercolour"},
  "aspect_ratio": "1:1",      // e.g. "1:1" | "3:2" | "2:3", default "1:1"
  "quality": "high"           // low | medium | high, default "high"
}

// response
{
  "status": "complete",
  "input_type": "text",
  "media": {
    "kind": "image",
    "mime_type": "image/png",
    "filename": "caret-imagine.png",
    "byte_length": 184320,
    "sha256": "9f86d081884c7d65…",
    "inline_base64": "iVBORw0KGgo…"
  },
  "provider": "my-image-tool",
  "request_id": "req_77af10"
}

byte_length and sha256 are required and must describe the bytes you are actually delivering. media.inline_base64 is the only image payload transport — there is no URL form and no data-URL form.

Generating the same person, pet, or object across many prompts is a backend behavior on top of this endpoint, not a contract change: see repeatable Imagine references.

8 · Idempotency

Every mutating request carries a client-generated client_request_id (≤128 characters). Replaying one must return the original result without re-running the work. The keyboard retries on connection drops, and a user who sees a network error and taps again should not be charged for two generations.

The keys, per surface: client_request_id for typed operations and session create; (session_id, seq) for chunk uploads; the session itself for session-consuming operations. Cache successes. Whether you cache failures is your call for the synchronous path — but for a 202 job and for session-consuming operations the answer is yes, or polling turns every failure into an infinite retry loop.

9 · Errors

Every non-2xx response, on every endpoint, is exactly this shape:

{
  "error": {
    "code": "session_conflict",
    "message": "session already consumed by dictate",
    "retryable": false
  },
  "request_id": "req_2bdad6"
}

message is shown to the user verbatim in the status row, so keep it short and free of internals. Never let a traceback or an HTML error page reach the wire — a client that cannot parse your error has no way to behave sensibly.

StatusCodes
400bad_request
401unauthorized
404not_found, unknown_session
405method_not_allowed
409chunk_checksum_mismatch, chunk_seq_conflict, session_conflict, backend_not_ready
410session_expired
413chunk_too_large
415unsupported_audio_codec
422input_invalid, unsupported_input_type, unsupported_aspect_ratio, unsupported_quality, audio_too_short, audio_too_quiet, no_speech_detected

The list is append-only. Clients meeting an unknown code fall back to retryable, so set that field truthfully — it is the only thing a future client can rely on. The V1 aliases (instruction, prompt, input.type: "audio") do not exist in V2; reject them with 422 input_invalid.

10 · Security posture

  • TLS is not optional. The keyboard refuses plain HTTP. Terminate TLS in a proxy or tunnel; your app process can stay on loopback.
  • Fail closed. No keys configured means every authenticated request is 401, not "open to everyone".
  • Constant-time key comparison, and never log the key — log the request_id instead.
  • One key per device makes revocation a matter of removing one string.
  • Audio is the sensitive part. Delete chunks as soon as a session reaches a terminal result, honor ACK as a purge, and expire whole sessions on a timer. Recordings that outlive their transcript are a liability with no upside.
  • Bound your inputs. Enforce the size limits above rather than trusting Content-Length, and reject session ids that could escape your storage directory.
  • Treat visible_text as untrusted. It is text from someone else's message and may try to instruct your agent. It is context for register, not a command.
  • Ask is read-only. The user has not inserted anything yet. A draft that books the meeting it is describing is a side effect nobody approved — say so in your prompt, every time.
  • A connection QR is a credential. If you offer one (see below), it carries the key itself — so generate it only on explicit request, never log or print the payload, write saved files owner-only, and tell the user that rotating the key is what revokes it.

10a · Connecting a device: caret-connect:v1

Caret can configure itself from a scanned code instead of a typed URL and key. If your backend offers one, this is the format it must produce — the client pins these bytes, so a one-byte disagreement scans and then fails, which is the worst kind of setup bug to debug from a phone. The caret-connect:v1 payload format is versioned independently of the API contract and is unchanged in caret/v2. 

minified JSON, keys sorted → UTF-8 → base64url, no padding → prefix
FieldMeaning
t Type, case-sensitive. "agent" for a backend the user runs. ("hosted" is reserved for Caret's own service and must omit u: the client pins its own canonical URL, so a hosted code that names one is an attempt to redirect a phone, and is refused.)
u Base URL, no trailing slash. Required for agent. https://, except loopback, RFC-1918 addresses and *.ts.net, where the transport is already private.
k The API key, 10–300 characters.

Worked example — the key is fake, and the bytes are pinned on both sides:

{"k":"caret_demo_key_1234567890","t":"agent","u":"https://agent.example.com"}

caret-connect:v1:eyJrIjoiY2FyZXRfZGVtb19rZXlfMTIzNDU2Nzg5MCIsInQiOiJhZ2Vu
dCIsInUiOiJodHRwczovL2FnZW50LmV4YW1wbGUuY29tIn0

Unknown fields are tolerated and passed through, so the format can grow. Reject an unknown t rather than guessing, and reject an agent payload with no u.

Gate generation on readiness: a code for a backend with no STT hands the user a keyboard missing its main surface and no explanation. The reference backend implements all of this in caret_backend/connect.py and exposes it as python3 -m caret_backend --qr --url <base-url>; see the Connect overview for the operator-facing version.

11 · Check yourself

The reference repository ships a conformance checker: standard-library Python, no knowledge of any particular implementation, so it works against a backend written in any language. 

python3 reference-backend/conformance.py \
    --base-url https://your-host --api-key "$CARET_API_KEY"

It exercises the parts that are easy to get subtly wrong — the one input model and the rejection of the removed V1 aliases, chunk idempotency, checksum rejection, stable request_id across polls, one terminal result per session — and skips what your capabilities say you do not implement. Exit code 0 means the keyboard will be happy.

A first smoke test by hand:

curl -s https://your-host/v2/health | python3 -m json.tool

curl -s -X POST https://your-host/v2/ask \
  -H "Authorization: Bearer $CARET_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"client_request_id":"smoke-1",
       "input":{"type":"text","text":"tell Sam I am running ten minutes late"}}' \
  | python3 -m json.tool

12 · The reference backend

If you would rather not write one, the repository includes a complete caret/v2 backend in about a thousand lines of Python with no dependencies. It is meant to be read as much as run: every rule on this page is implemented once, in an obvious place. 

cd reference-backend
python3 -c 'import secrets;print(secrets.token_urlsafe(32))'  # generate a key — copy the output
export CARET_API_KEYS=paste-the-key-here                      # paste this into Caret
python3 -m caret_backend --port 8787

python3 -m unittest discover -s tests     # hermetic tests, no network, no model calls
python3 conformance.py --base-url http://localhost:8787 --api-key "$CARET_API_KEYS"

Your agent plugs in as a command line — anything that takes a prompt and prints a reply on stdout: 

export CARET_AGENT_COMMAND='my-agent --quiet {prompt}'   # or stdin, if no {prompt}
export CARET_STT_COMMAND='whisper-cli -m model.bin -f {audio} --no-timestamps'
export CARET_IMAGE_COMMAND='my-image-tool --prompt {prompt} --out {out}'

Ask and Imagine stay off — and say so in capabilities — until you configure them. Dictate is the exception: with no STT adapter resolved the backend reports not_ready and --check fails, because a backend that cannot take speech is not a Caret backend. Full configuration, TLS notes and the per-agent details are in the reference backend's own README.
